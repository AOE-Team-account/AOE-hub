# AOEhub — Project Context

**Read this first.** This file captures every real decision made while designing AOEhub, across a long planning conversation. `hub-prototype.html`, if it's sitting in this same folder, is the authoritative *visual and interaction* reference — layouts, copy, component behavior. This document captures the *why*, the *formulas*, and the *non-visual architecture* that don't show up just from reading the HTML. **A separate file, `MARKETPLACE-UPDATE.md`, holds the planned marketplace update. It is deliberately kept apart from this one — do not merge them.**

## What this is

AOEhub (full name: **Alpha Omega Education**) is an education hub for homeschool, unschool, and school families. Its two boards are **free, always**, and a separate marketplace is planned for a later update (see "Planned future update: marketplace"). It is built around a core philosophy: **you don't copy someone else's path, you walk your own, using their experience so you don't repeat wrong turns.** "Education is an atmosphere, a discipline, and a life" is the pull-quote that captures the spirit. It's for children to learn *and* for parents/guardians/teachers to keep learning too.

Domain: **aoe.ai** (already owned, registered via Namecheap). It currently hosts an existing AOE curriculum site that will be migrated into the hub as its first real content.

## The two spaces

- **File Board** — free curriculum, books, cards, games, printables, songs, apps. Anyone can upload, download, remix. Points are earned here.
- **Experience Board** — real stories *and* philosophy discussion, merged into one space. There is **no separate "Our Philosophy" tab** — it was deliberately folded in, because philosophy belongs to everyone, not just admins. A "Philosophy" tag/chip lets people filter for it, alongside "Starting out," "Milestones," "Struggles & lessons," "Curriculum reviews," "Reflections," and **"Question"** — questions the hub AI couldn't answer and offered to post (see RAG below) carry this tag, and the chip filters the board down to just those. Anyone can post philosophy content directly (no admin review gate) — this replaced an earlier design where only admins could post curated philosophy.

**These two spaces are free, always.** A marketplace, where members can buy and sell, is planned as a *separate* third space in a later update. It is never mixed into these two, and nothing on them starts costing money.

**Groups (public and private) was removed entirely as a feature — not merged, not simplified, fully deleted from the design.** This resolves what was previously an open question in this file about whether "remove groups" meant removing the public/private distinction or removing the feature entirely — confirmed: entirely. Every other section of this file has been updated to remove references to it accordingly. **Everything on the hub is now public by default**: an idea, question, or experience goes to the Experience Board; a file goes to the File Board. There's no private space anywhere in the hub anymore.

## Points system (exact formula)

- 1 point per view (rate-limited to once per person per day, to prevent gaming)
- 5 points per download
- 3 points per question/comment left on your post
- 10 points per remix of your file
- **Search ranking** uses a *log-compressed* version of these points (so one huge hit doesn't permanently bury newer good content) — but a user's **profile total is a simple, honest sum**, not compressed.
- Points only ever come from File Board and Experience Board activity.
- Experience Board's own display order stays **chronological**, not popularity-ranked, even though its posts contribute to points — this was a deliberate choice to keep it from becoming a popularity contest.

## Trust & safety

- **Moderation powers now live in the 5-tier Roles system below** (Creator/Watchers/Deacons/Answerers/Verified) — this replaces an earlier, simpler "exactly 4 admins" model entirely; don't build both.
- **Report button** on everything: files, posts, and comments.
- Report reasons (structured, not free text): scam/money request, off-topic, inappropriate content, paywalled/costs money, copyright/not their work, something else.
- **The moderation panels (Creator, Watchers, Deacons) never show a default scrollable list of *people*** — an account appears only when reported or searched for by name/email. This is deliberate: it prevents an accidental misclick on "delete" or a role change while idly scrolling. **Content is different**: Watchers and the Creator can browse *all* posts and files, and Deacons all posts, whether or not anyone reported them, because they need to catch problems nobody reported (see Roles below).
- **Authorship field is required at upload**: Original / Remix / Not my work. Remixing auto-links back to the original creator — this is structural, not something the uploader has to remember to add.
- File posts keep a lightweight **version history** (changelog note on update) so old download links don't silently break for people who already built around a previous version.
- **Every uploaded file must be scanned for malware before it's downloadable, using self-hosted ClamAV, run on Google Cloud Run** (see Tech Stack for the full reasoning — VirusTotal was evaluated and ruled out due to its terms-of-service restriction against commercial/service use and its punishing enterprise pricing). Flagged files get quarantined automatically, never shown publicly.
- **Multi-file bundling**: one upload post can contain several files (e.g. different language versions of the same document, or chapter-by-chapter curriculum). Each file gets its own label and its own download button — this avoids forcing someone to split one logical resource into many separate posts.
- **The hub takes no responsibility for a user being scammed by another user** — this should be stated plainly in the Terms of Service. This is standard practice for platforms like this, but still worth a real legal read for the specific jurisdiction, same as the DMCA point below.
- **No public announcements about violations (decided by Clara).** When something is reported, reviewed, and deleted, nothing is announced publicly. Instead **the person who posted it receives a private message saying what was deleted and why** (e.g. "Your file was deleted because it violated our rules: Copyright — not their work"). The reason is picked by whoever deletes it, from the same structured list as report reasons. This keeps the "human review before action" principle: a real person with delete power (Creator, Watcher, or Deacon within their scope) decides — never automatic. *(This replaces an earlier draft in which confirmed violations were announced publicly via a pinned Experience Board post, and resolves the old open question of which tier confirms a report: whoever holds the delete power for that kind of content — Watcher/Creator for posts and files, Deacon for posts.)*
- **Content policy wording principle**: the "no scams" rule and any inappropriate-content rules must be kept as separate, distinct rules — never worded in a way that conflates a protected characteristic (e.g. sexual orientation) with prohibited content. The policy targets actual content/safety issues (scams, inappropriate content, off-topic material), not categories of people. This was an explicit early correction in this project's planning and should be treated as a hard constraint when the actual policy/rules page gets written.
- **Every reviewer action is logged, and deleted content goes to a trash, not purged.** The **Activity log** records every deletion, notice (added, edited, removed), dismissed report, and warning by the Creator, a Watcher, or a Deacon: **what, when, and who did it**. **Only the Creator** can see the Activity log and the Deleted items (trash) — both are tabs in the Creator panel. The Creator can **undo** a deletion (including one the Creator made), a notice, a notice removal, a dismissed report, or a warning with one button (see Roles → Creator undo). Restoring puts a deleted item back exactly where it was, and that is logged too. *Not yet decided:* how long the trash keeps an item before it is really removed (suggest a fixed period, e.g. 30 days, stated in the panel).

## Roles & moderation powers (expanded from the original 4-admin model)

This replaces the earlier simpler "exactly 4 admins" model with a more detailed 5-tier system. **Confirmed: Groups (public and private both) is removed entirely as a feature**, not simplified to one kind — this was previously an open question in this file, now resolved.

**Five tiers:**
1. **Creator** — total power, and superior to every other tier. The Creator can **do everything Watchers and Deacons can do, and see everything they can see**: every post, every file, every report, the original of anything, and the actions notice / warn / delete / dismiss. On top of that the Creator can **undo** anything a Watcher, Deacon, or the Creator did (see "Creator undo" below), **give and take away every role — including removing a Watcher or Deacon from the position they were appointed to** —. **There is no "delete the hub" feature, button or procedure in the app** (Clara, 2026-10-09: removed on purpose; shutting the hub down, if ever needed, is done outside the app by the owner of the hosting and database accounts). **Verifying** a user means the Creator agrees with that person's ideas. **Cannot post ideas or files** — to post, the Creator uses an ordinary user account. Reaches the Creator panel through the sign-in access code (see "Access to the Creator panel" below). Creator panel tabs: **Review** (reports + browse everything), **People & roles**, **Deleted items**, **Activity log**, **Hub** (announcements).
2. **Watchers** — see every post, comment and file and every report (post, comment *and* file reports), and can act on things nobody reported (they see the whole hub, not only reports). They can **view the original** of anything, **add or edit a notice**, **warn** the person who posted it (a private message), **delete** posts, comments and files, and **decide each report**: add a notice / warn / delete / dismiss. **Posting, uploading and selling are not part of the Watcher panel** — nothing in the panel lets a Watcher post, upload a file or list an item. As an ordinary member in their normal place they post, upload, comment (and, once the marketplace exists, sell) like anyone else (see "Same account, private panel").
3. **Deacons** — same as Watchers but **posts and comments only, never files** (Clara, 2026-10-08; posts-only before comments were added): they see all posts and comments and the reports on them, and can **view the original**, **add or edit a notice**, **warn** the poster, **delete**, or **dismiss** a report on a post or comment. Files and file reports are never shown to a Deacon (those go to Watchers and the Creator). **Posting, uploading and selling are not part of the Deacon panel** either; in their normal member place they do all of that like anyone else (see "Same account, private panel").
4. **Answerers** — post ideas, files, and comments like anyone; their posts, files, and comments are **pinned to the top**. Badge: a single letter **A**.
5. **Verified** — badge: a single letter **V**; their comments are **highlighted**. Can **pin one of their own posts and one of their own files** to a "From verified voices" section (see "Verified voices" below). Otherwise an ordinary user who can do anything an ordinary user can.

**Roles combine.** A person can be **Answerer and Verified at the same time**, and holding Watcher or Deacon does not affect either of those (or the other way round). Roles are independent. (The prototype also lets one person hold Watcher and Deacon together; nothing forbids it.)

**Same account, private panel — not a separate account (decided by Clara, 2026-10-08).** Before anyone is a Watcher or Deacon they are a normal member, and being a Watcher or Deacon is simply **another job on top of that account**. In their **normal member place** they can post, upload files, comment and, once the marketplace exists, upload items to it, exactly like any member. The role adds a **link/button on their own profile** ("Open Watcher panel" / "Open Deacon panel") that only they can see; it opens their panel (the reports queue and the whole hub in a Watcher/Deacon view). **Inside the panel they cannot post, upload files or list marketplace items**: the panel is for reviewing only, and the server must refuse those actions on any panel request, not just hide the buttons. The link disappears the moment the role is removed, and the person keeps their ordinary account. Answerers and Verified get **no** button — only the badge.

**Consequences to build.** (1) **Reports about a staff member's own items (decided by Clara, 2026-10-08).** A Watcher or Deacon can **see** every report, including a report about something they posted, uploaded or commented as an ordinary member, but **cannot dismiss, delete, warn or add a notice on their own item**. Their panel shows it with "This one is yours" and a View-original button only. **Any other Watcher or Deacon (within their scope) and the Creator can dismiss, delete and warn on it as normal.** Nothing goes to a special queue, and the other reviewers see the author as an ordinary member, so the anonymity rule holds. This is the no-self-review rule (Warnings → rule 5), now covering comments too; the server must enforce it on every action. **Scope reminder:** a **Watcher** can dismiss, delete and warn on **posts, comments and uploaded files**; a **Deacon** only on **posts and comments**, never files. (2) "May post, upload or sell" is decided by "is an ordinary account in good standing" (not restricted), never by role, and panel requests are a separate permission set that contains no posting or selling. (3) The Creator's own rule is unchanged: the Creator role does not post; to post the Creator uses an ordinary user account.


**Anonymity rule (Clara): nobody should be able to tell who is the Creator, a Watcher, or a Deacon.** Creator, Watcher, and Deacon have **no badge** and show nothing publicly; their buttons, panels, and actions are invisible to everyone else. Only Answerer (A) and Verified (V) are ever visible. **Who holds these roles is known only to the Creator and to the Watchers and Deacons themselves** (Clara, 2026-10-08); because a Watcher or Deacon posts from an ordinary member account, their posts, files and comments look exactly like anyone else's. Anything a reviewer does that readers can see (notices) must therefore not reveal who did it.

**Notices (decided by Clara).** A notice appears above the post or file and **names the tier, never the person**: "Notice from a Watcher: content below is not fully correct" (that is the default text; the reviewer can write their own). A Deacon's reads "Notice from a Deacon", and the Creator's reads "Notice from the Creator". This keeps the anonymity rule: it says a Watcher/Deacon/Creator acted, not which account. **A Watcher or Deacon can never edit, replace, or remove anything the Creator added (decided by Clara)** — a Creator notice shows them a lock ("only the Creator can change it") instead of Edit/Remove buttons, and the server must refuse the change even if someone forces the request. Watchers and Deacons can still edit or remove notices that were not added by the Creator, and the Creator can change or undo any notice from the Activity log. (Hub announcements are different and read "from AOEhub".)

**View original.** Every report card and every item in the "Browse the hub" list has a **View original ↗** button. In the real build it opens the real post or file page in a reviewer's view, exactly as readers see it (including any notice, the file list, and the "Translated from … · Show original" toggle for other-language content), with a way back to the panel. The prototype opens a preview window that shows the same information.

**Warn.** The reviewer picks a reason from a fixed list; **the reason sets the level (green / yellow / red), the reviewer does not** — see "Warnings, restrictions & evidence" below. The dialog shows the level, the person's current record, and exactly what the count will be after this warning (including "this is the 10th green", "this makes 5 yellows", "this puts the account at 3 red: restricted for one week"). The person gets a private message. Nothing is public. Watchers and the Creator can warn about posts and files; Deacons about posts. **Only the Creator can undo a warning.**

**Creator undo.** From the Activity log (and from a person's record) the Creator can undo: a **deletion — including one the Creator made** (item comes back exactly where it was), a **notice** (added or edited → the previous notice, or none, returns), a **notice removal**, a **dismissed report** (the report re-opens exactly as it was), and a **warning** (the counts are recalculated; a restriction that was caused by it is lifted; the person is told the warning was withdrawn; the warning stays in the record marked "undone" and is not counted). Deletions, notices, and dismissals undo **newest change first, per item** — an older change on an item stays locked until the newer one is undone, so nothing gets tangled; warnings can be undone in any order because the counts are always recalculated from the history. Each undone entry shows "Undone by Creator" with the time. Restoring from Deleted items does the same thing as undoing a deletion.

**Giving and removing roles (Creator panel → People & roles).** Search for the person by name or email (nobody is listed until searched). Select them: the panel shows a card, "You are changing roles for: [name, email]", with four toggles (Watcher, Deacon, Answerer, Verified), each with a one-line explanation of what it does. **Every change needs a confirmation step** that names the person and says what will happen. A "Who has a role right now" list shows everyone holding a role, with a **Remove [role]** button for each role they hold, using the same confirmation ("Remove Lin H.'s Deacon role?"). **Removal is immediate**: a Watcher/Deacon's profile button disappears and, if their panel is open at that moment, it closes; a badge disappears from the board; the person is told; they keep their ordinary account; and the Creator can give the role back at any time. A removed Watcher or Deacon can no longer act — the server must check the role on every action, not just hide the button (see "Staff-account protection" below). **Promotion happens only here — never from a report card.** (An earlier mockup put a "Promote author" dropdown on the report card; Clara found it confusing because it was unclear *which person* was being promoted, so it was removed.)

**Messages people receive when a role changes:**
- **Watcher / Deacon**: an unmissable on-screen message **and** a notification — "You have been chosen by the Creator to become a Watcher/Deacon. You can now …" (listing that tier's powers) — and the profile button appears.
- **Answerer / Verified**: a notification, and the badge appears next to their name. No profile button. (The prototype shows the same on-screen message for all four roles as a simplification; the requirement only insists on it for Watcher/Deacon.)
- **Removal**: a message of the same kind, and the button or badge disappears.
- Messages that arrive while someone is signed out are shown one after another when they next sign in.

**Report resolution.** For each report, the reviewer can **view the original** and then chooses **add notice / warn / delete / dismiss**. Watchers and the Creator handle post and file reports; Deacons handle post reports only. On delete, the reviewer picks a reason and the author gets a private message with it (see Trust & safety). Nothing is announced publicly.

**Hub announcements (assumption — confirm).** The Creator cannot post ideas or files, but a hub-level announcement that pins to the top of the Experience Board is kept as a Creator-only tool in the Creator panel (Hub tab). It reads as coming from **AOEhub**, not from a person, so it does not break the "Creator can't post" or the anonymity rule. Clara's answers covered ideas and files, not announcements, so this is an assumption.

**Badge visual design (built in the prototype).** A small circle with a single letter: **A** in a green tint, **V** in an amber tint. Tapping a badge opens a short plain-language explanation of that tier. Pinned comments (Answerer) sit at the top with a "Pinned" label; Verified comments have a highlighted background.

**Hard product requirement: the Creator/Watcher/Deacon power interfaces must be clean and simple, operated entirely through buttons and forms — never requiring anyone to touch or edit code directly.** Promoting someone, adding a notice to a post, deleting content, reviewing reports — all of it needs to be a normal, non-technical admin panel, not something that asks a non-developer to get into a config file or a script. This is a firm constraint on how Phase-appropriate work should build these panels, not a nice-to-have.

**A real, acknowledged limitation worth being explicit about: text alone can't fully specify a visual design, and the person building this and the person describing it may not be picturing the same thing.** This isn't a problem to write around with more words — it's a reason to build a visual mockup and check it against what's actually intended *before* Claude Code builds the real interface, rather than describe it more and more precisely in text and hope it lands. The prototype (`hub-prototype.html`) now contains working versions of the badges and all three panels (Creator, Watcher, Deacon) — use it as the visual and interaction reference, and check the real build against it before calling it done.

**Access to the Creator panel — the sign-in access code, built as a second step rather than the only secret.** Clara's design: at sign-in, entering a specific code leads to the Creator panel, and the Creator's edits always remain superior. Build it as: the Creator signs in with a **real Creator account (normal secure login, ideally two-factor)**, *and then* the access code is checked as an additional step. The code alone never grants anything; wrong attempts are rate-limited and logged. The field is hidden behind a plain "Have an access code?" link and is **cleared whenever the login form is closed or reopened** (the prototype does both — it caught a real bug where a leftover code silently re-entered Creator mode on the next login). The prototype's demo code `AOE-CREATOR` and the hint shown under the field are scaffolding only and must never ship. Reason for the second step: if a code alone ever leaks, gets guessed, or is logged, whoever has it gets total control (including deleting the whole hub) with no account trail. **Watchers and Deacons use no codes at all** — their roles are stored against their accounts in the database, and the profile button appears or disappears automatically. *This is a recommendation layered on Clara's code idea — Clara to confirm.*

**Panel architecture: a real protected page, not a hidden div (Clara's call).** The Watcher, Deacon, and Creator panels are built as their own **protected route** (e.g. `aoehub.com/mod`, `aoehub.com/creator`), not markup that merely sits hidden on the same page until a client-side toggle reveals it. Clicking the panel button takes the browser straight there — **nothing is typed, no code is shown** — because entry rides on the person's existing signed-in session, the same one the rest of the hub already trusts. What makes this secure is not that the URL is secret: it's that **every single request into that route, and every action taken on it, asks the server fresh "does this account currently hold this role?"** A bookmarked or screenshotted link is therefore never dangerous on its own — without a live, current session belonging to someone who still holds the role, it does nothing, the instant the role is removed. (This is the same rule as Staff-account protection #1 and #2 below, just spelled out as page architecture.) This also means the link is never a "code to save" the way an access code would be — nothing worth protecting sits in the URL itself, so there is nothing for a removed Watcher or Deacon, or anyone they showed the link to, to hold onto.

Deliberately **not** built as a secret link that works on its own (a "bearer link/token"), where simply knowing the URL is enough to get in. That pattern leaks in ordinary ways — browser history, screenshots, pasted into a chat, server access logs, and the `Referer` header sent to any third-party resource the page happens to load — and once it leaks, whoever has it gets in regardless of whether the real owner still holds the role, unless something else re-checks that live. Session-plus-fresh-server-check avoids all of that by design.

**Build order: same-domain route now, a real subdomain later.** `aoehub.com/mod` and `aoehub.com/creator`, gated by a server-side role check on every request, deliver everything described above with no extra infrastructure — one app, one deploy, no cross-domain cookie handling. Splitting these onto a literal subdomain (`mod.aoehub.com`) is a good **later hardening step**, not a prerequisite: its real benefit is cookie/session isolation — a moderation session living only on its own subdomain can't be reached by a bug (e.g. a scripting attack) on the public-facing boards, which is a genuine concern here specifically because the File and Experience Boards are full of user-submitted, translated, remixed content and so carry more attack surface than a locked-away panel would on its own. Worth doing once there's bandwidth for the added complexity (DNS, a certificate, handing a session from one to the other); not required to get "a removed Watcher or Deacon is instantly and permanently locked out," which the per-request check already guarantees by itself.

**If the Creator is locked out (Clara: "add another way").** Wrong-code lockout, a lost password, or a lost two-factor device must never lock everyone out of the hub. Three layers:
1. **Recovery keys.** The Creator creates a set of one-time recovery keys (the prototype makes 6, format `AOE-RK-XXXX-XXXX`), shown **once**, to be saved **offline** (printed or in a password manager, never on the sign-in device). Each key works **once**; creating a new set **replaces** the old set. Store them **hashed**, like passwords. In the sign-in box a "Locked out?" link opens a recovery-key field. A valid key gets the Creator in, resets the wrong-code counter, and is logged; the real build also **emails the Creator** every time a key is used. Wrong keys are rate-limited (the prototype locks after 5). The Creator panel's Hub tab shows how many keys are left and a list of recent sign-in events (wrong codes, recovery-key use, new keys created).
2. **Recovery by email with a waiting period** (real build): a recovery link to the Creator's registered email that only takes effect after a delay (e.g. 24 hours) with an alert sent to every recovery address, so an attacker who breaks into one inbox cannot take over instantly.
3. **Last resort:** whoever owns the hosting and Supabase accounts can restore the Creator role directly in the database. Write the exact steps in a `RECOVERY.md` in the repo (keep it out of the public site). This is the safety net underneath the safety net.
The wrong-code lock should be **time-based in the real build** (e.g. 15 minutes), not permanent; the prototype locks until reload to show the behavior.

**Staff-account protection (Clara's requirement).** A Watcher or Deacon who has been removed, who turns bad, or whose account is hacked must never be able to do serious damage. The rule of thumb: *the server decides who is allowed in on every single request; hiding a button is never protection.*

1. **Removal is instant and total.** The role is stored against the account and checked **on the server on every request** — opening a panel page, loading its data, and every action (notice, warn, delete, dismiss). The moment the Creator removes a role: bookmarked or saved panel links stop working; an already-open panel or open dialog stops working (a half-finished delete must not complete); the person is told; and they keep only their ordinary member account. Removal deletes the role itself, not just a flag on a button. (See "Panel architecture" above for how the panel itself is built so this holds.)
2. **No codes to save.** Watchers and Deacons have **no access codes of any kind** — their access is purely "this account currently holds the role". Nothing they could have written down or saved gives access after removal. The only code in the system is the Creator's, and it works only *together with* the Creator's real login (see "Access to the Creator panel"), is limited to **5 wrong tries then locked** (the prototype does this), and failed attempts are logged and shown to the Creator.
3. **Coming back needs the Creator.** After removal nobody can re-enter their panel unless the Creator appoints them again — a brand-new, explicit appointment (with the normal confirmation). Nothing carries over from before: not old sessions, not an old lock, not automatic reinstatement.
4. **Nothing is ever really gone.** Deletions are soft (trash), every action is in the Activity log, and the Creator can undo any of it. There is deliberately **no automatic lock** that suspends a reviewer for deleting a lot (Clara decided against it): protection comes from instant role removal, the Creator seeing everything, and being able to undo everything.
5. **Watchers and Deacons handle content only.** They cannot delete or suspend accounts, change anyone's roles, undo anything, see the Activity log, Deleted items, or the Accounts tab, or touch the hub itself — those are Creator-only. **Account deletion is Creator-only (confirmed by Clara).** They can warn, and can *report* an account to the Creator once it reaches 5 red warnings — the Creator decides.
6. **Hacked-account defenses (backend requirements, not shown in the prototype).** Recommended: require **two-factor authentication** on any account before it can be made a Watcher or Deacon; require the **password again when opening the panel** (step-up); end panel sessions after a short idle time (e.g. 30 minutes); email a confirmation when a staff account signs in from a new device or place. The Creator's Remove-role button is the emergency stop and works instantly.

**All accounts** (any tier) can customize their profile picture and decorate their account (profile frames, account backgrounds, post fonts, etc.) — cosmetic personalization available to everyone, not tier-gated.

**RAG "I don't know" flow (resolved).** When the AI can't answer confidently it says so plainly instead of guessing, and **asks whether to post the question on the Experience Board** for people to answer. If the user says yes: (1) the question is posted as an ordinary post under **the asker's own account** (also listed in their My posts), marked as an open question; (2) **every Verified member and Answerer gets a notification** that a question needs an answer; (3) anyone can answer or comment, but **Answerer replies are pinned to the top and Verified replies are highlighted**; (4) **the asker is notified each time someone answers**. It does **not** go to Creator/Watchers/Deacons — they don't answer questions as their tier. Posting needs an account (a logged-out "yes" hits the normal sign-in wall). *Consideration, not decided:* notifying every Verified member and Answerer for every unanswered question could become noisy as the hub grows; a per-person mute or frequency setting is a cheap mitigation. **What feeds the AI (decided by Clara, 2026-10-09):** answers to Question posts do feed the hub AI's knowledge, but **not every comment or answer**: only those written by **Answerers and Verified members**. **If such a comment or answer is deleted, by anyone and for any reason (its author, a Watcher, a Deacon, the Creator, or the deletion of the account), it must also be deleted from the AI's data**, so the AI can no longer quote it. Build notes: store which post and comment each piece of AI knowledge came from so it can be removed exactly; have the AI say when an answer comes from a community answer; follow-ups for Clara: should a restored (undeleted) answer go back in, should a comment with a Watcher's "not fully correct" notice stay in, and what happens to earlier answers if the person later loses the Answerer or Verified role. The Terms (lawyer) should say that answers members post can be used to help answer other members' questions.

## Warnings, restrictions & evidence (Clara's rules)

Reviewers (Creator, Watchers, Deacons) can **warn** a person. A warning is private, counted, and stays on the person's record unless the Creator undoes it. Enough warnings lead to a restriction and, in the worst case, to the Creator deleting the account — **never** to an automatic deletion.

**Three levels — the reason sets the level, not the reviewer:**

| Level | Reasons (fixed list — no free text) |
|---|---|
| **Green** (light) | Off-topic / not education related |
| **Yellow** (medium) | Ads or self-promotion · Wrong ideas (as defined in the content policy) · *assumed:* Paywalled or costs money · *assumed:* Copyright — not their work |
| **Red** (severe) | Scam or asking for money · Harmful ideology or harmful content · *assumed:* Inappropriate content |

Levels are shown with **words as well as colour** ("2 red · 1 yellow"), for colour-blind readers. **Policy wording:** "wrong ideas" and "harmful ideology" must be written into the content policy as concrete, behaviour-based rules (for example hate speech, harassment, threats, scams, spam) before launch. "Wrong" on its own is too subjective for something that can end an account, and it conflicts with the content-policy principle earlier in this file (target actual content and safety issues, never categories of people) and with the hub's philosophy that families walk their own path. Reviewers pick from the fixed list; they never judge on taste.

**Counts grow on their own; history is never deleted.** Each person's standing is *calculated from their full warning history*: **10 green = 1 yellow**, and **5 yellow = 1 red** (yellows that came from greens count). So "a green can become a yellow, a yellow can become a red" happens by accumulation. The individual warnings stay on record; only the displayed count converts. Undoing a warning simply recalculates.

**Emergency suspension for a severe violation (decided by Clara, 2026-10-09).** Waiting for 5 red warnings is too slow for a serious case such as a child-safety concern. **Any Watcher or the Creator can suspend an account at once**, pending the Creator's review. A suspended account cannot sign in, post, upload or comment, and its content is hidden while the Creator reviews it. The suspension needs a reason from a fixed list, is recorded in the activity log, and the person is told. The Creator then lifts it, applies a normal restriction, or deletes the account (account deletion stays Creator-only). Details still to settle when this is built: whether Deacons may also suspend (Clara's example named only Watchers and the Creator, so no), and that a reviewer can never suspend themselves (no self-review). Not in the prototype yet.

**Restriction.** When a person reaches **3 red**, their account is **restricted for one week**: they cannot **post ideas, upload files, or comment** (this also covers remixing and the hub AI posting a question for them). They can still read and download. They are told on screen and in notifications, a banner with the end date shows on every page, and it ends by itself. It applies once when the count crosses 3 (a 4th red does not restart it — see open questions). If the Creator undoes warnings so the count drops below 3 while restricted, the restriction is lifted.

**At 5 red, the account can be reported to the Creator.** Watchers and Deacons get a **Report to the Creator** button on that person's record **only at 5 red** (so a report can never be used to target someone with a clean record; one open report per person). The Creator then sees **everything on record** — every warning with who issued it and a snapshot of the content, everything the person posted, every action taken about them — and decides: **delete the account** or **dismiss the report**. (Clara wrote "three reds = one week restriction; after that, two more red warnings and you can be deleted." Read as: 3 red → restriction; 5 red → report.) **Only the Creator can delete an account**; the Creator can also **restore** it from the Accounts tab.

**Who sees what.** The warned person gets a private message with the level, the reason, their current record, and a note that repeated warnings lead to restrictions. **Watchers, Deacons, and the Creator see the person's colour and number** (e.g. "2 red · 1 yellow", "restricted") next to their name on their posts and files, and can open the person's record. It is never shown to ordinary members or the public. Only the Creator sees *who* issued each warning, the content snapshots, and the full evidence. **Only the Creator can undo a warning.**

**Everything is saved as proof (Clara: "if they sue us, we have proof they went against our violations").**
- Whenever a warning, notice, dismissal, or deletion happens, store a **snapshot of the content at that moment** (the text, the file names and a copy of the files, the reason, the rule, who acted, the exact time), so the person editing or deleting it afterwards cannot erase it.
- The evidence store is **append-only** and **only the Creator can read it**. Recommended: a "download this person's record" button for handing to a lawyer.
- **Deleting an account removes their posts and files from the hub, but their record and evidence are kept.** The Accounts tab lists deleted accounts with their evidence; the Creator can restore one.
- **Needs real legal review (same category as DMCA):** how long to retain evidence; how this squares with privacy laws that let people ask for erasure (they generally allow keeping data needed for legal claims — but get advice); and the Terms of Service and Privacy Policy must say plainly that records are kept after deletion for safety and legal purposes. Copyright warnings should also feed the hub's DMCA repeat-infringer policy. **Added 2026-10-09:** keeping a *copy* of an uploaded file as evidence is a separate legal question, because specific rules cover the worst categories of illegal material (reporting duties and how it must be stored). Until a lawyer says otherwise, store a **fingerprint (hash) of a deleted file, not the file itself**. See Still open item 26.

**Strict rules for reviewers (draft — Clara/Creator to edit).** The prototype includes a "Rules for reviewers" window in both panels. The rules the design enforces or requires:
1. **Every action needs a reason from a fixed list** — delete, warn, dismiss (a report), and add a notice each require one, and it is recorded. No reason, no action.
2. **The reason sets the warning level**; the reviewer cannot pick or change it.
3. **Counts, restrictions, and reports follow the fixed thresholds above** and cannot be skipped or forced.
4. **Only the Creator** deletes accounts, undoes warnings, or changes a notice the Creator added.
5. **No self-review** (enforced on the server; the prototype now enforces it too): a reviewer cannot dismiss, delete, warn or add a notice on their own posts, comments or files, or warn themselves. They can still **see** reports about their own items; another Watcher or Deacon (within scope) or the Creator handles them. The same will apply to a reviewer's own marketplace listings.
6. **Everything a reviewer does is recorded** with their name and the time and kept as evidence; misuse can cost them the role.
7. Deleting is never final: the Creator can restore anything.

**Verified voices — self-pinned, not algorithmic, never overrides search (Clara's call).** A Verified person can pin **one post and, separately, one file** — their own only — to a small, clearly labeled "From verified voices" section at the top of the Experience Board and File Board respectively. What this is *not*, and why:
- **It never touches search.** Clara's first version of this idea pinned Verified content to the top of search results; the problem is that overrides what actually matches what someone typed, so a better answer could get buried under an older pinned one. Resolved: search stays relevance-first, full stop; pinning only affects the board's own feed.
- **It is not algorithmic.** An earlier build of this picked a Verified person's most recent unflagged posts automatically. Clara rejected that: a badge earned once isn't the same as every future post being good, prolific posters would quietly dominate the section by volume rather than merit, and a flagged post could sit featured until someone happened to review it. Resolved: nothing appears unless the person themselves chooses to pin it, from a small panel on their own profile page.
- **A notice or a warning un-pins it immediately — and clearing the notice, undoing the warning, or having Verified removed and later restored does not bring it back on its own.** The pin is actually cleared, not just hidden, specifically so nothing "quietly returns" without the person making a fresh, deliberate choice to pin it again. This was an explicit correction from Clara after an early build auto-restored a pin once its flag was lifted.
- **Bounded.** One pin per person per board keeps it from growing into a pile; the section itself is capped (prototype: 3) as a second safety margin if many Verified people ever pin at once, and it hides entirely rather than showing an empty label when nobody currently qualifies.

## Access model (logged-out vs signed-in)

- Logged-out visitors can **freely browse and read** File Board and Experience Board (including Philosophy-tagged posts) — no account needed to look around, and the tab bar lets them move directly between the two boards without a detour through the marketing page (that detour was a real bug in an earlier prototype build — a signed-out visitor could reach the Experience Board from the File Board, but not back, because the File Board tab was hidden while signed out with no other route to it).
- They **cannot**: download, post, comment, remix, follow, or report. All of these are gated behind sign-up.
- **Accounts require the user to be 13 or older** (a simple age attestation at sign-up, e.g. "I am 13 or older"). This is a real legal requirement, not just a preference: COPPA requires verifiable parental consent before collecting personal information from anyone under 13, and 2025–2026 rule amendments tightened this further — full compliance (verifiable consent flows, special data handling) is a heavy lift not appropriate for this project's scale. Requiring 13+ for the account itself is the standard approach most platforms take; it doesn't stop younger children from benefiting from the hub's content, since a parent's account can represent the family. Get a real legal read on this specific point given how recently the rules changed — same category as the DMCA requirement below.
- **Language is not a separate onboarding question.** The header's language switcher (available even logged out, per Translation below) is what a user has already selected by the time they sign up — that selection carries into their new profile automatically at the moment of sign-up. No dedicated "what language" onboarding step is needed.
- **Sign-up triggers a short onboarding. One question is required (where you are, below); the others are optional as a set** (a "Skip for now" option is always available, but it also asks for the required question first):

Continue and Skip are both blocked until one is chosen. It is the member's own statement (not checked by IP address), is saved to the account, and can be changed any time in profile settings. Two **separate** taxonomies — don't conflate them:
- **Sections** (subject/category): Curriculum, Games, Books, Cards, Songs, Art projects, Printables, Apps.
- **Media type filter** (file format): Video, Audio, Image, Document, Game/App.

**Uploading apps, web apps, HTML content, and games — this needs a real upload mechanism, not yet built.** The "Game/App" media type category already existed in the design, but the actual upload/hosting path for it was missing. Documents/audio/video route to Internet Archive as normal; anything meant to run *live* in the browser (a web app, an HTML5 or Unity WebGL game) needs a different path — accept the bundle, host it via Cloudflare R2/the hosting layer, and serve it so it actually runs in-browser, not just downloads as a file (Internet Archive isn't built for this — see the Hosting section of the fuller conversation summary for why). **Upload format: one `.zip` with the whole project inside and an `index.html` at the top level.** The prototype's upload form shows this hint when Game or App is chosen.

**Games, apps and web apps that are too big for the free storage (decided by Clara, 2026-10-08).** These files cannot go to the Internet Archive (it cannot run them live), and big bundles can outgrow Cloudflare R2's free allowance (10 GB of storage in total; downloads from R2 are free). The handling:
1. **Per-bundle size cap of 50 MB (confirmed by Clara, 2026-10-08)** for hosted games and apps, measured on the uploaded `.zip`. Show it on the upload form next to the `.zip` hint. A small cap also keeps the free 10 GB of R2 going a long time (several hundred games).
2. **Over the cap, the post becomes a link-out.** It is still a normal File Board post (description, preview, authorship label, discussion thread), but the play or download button goes to a place the creator hosts. Starting list of approved hosts: **GitHub, itch.io, Steam, or the creator's own site.**
3. **The approved-host list is deliberately open.** Store it as data (not code), expect it to grow, and give members a way to ask for another host to be added; a Watcher or the Creator approves it. Hosts that make sense to add later include GitLab, Google Drive or Dropbox (downloads only), Newgrounds, and Game Jolt. Do not hard-code the list.
4. **Every link-out carries a visible label: "Hosted outside AOEhub."** The label sits on the post and next to the button, and clicking opens the other site in a new tab (never inside the hub). The label's short text says: "This file is on another website. AOEhub has not scanned it and cannot guarantee it is safe or genuine. Only open it if you trust the creator." Link-outs are reportable and reviewable like any other post, and a Watcher can remove one.
5. **Terms of Service gets a matching clause** (see Legal): AOEhub does not host, scan or control link-out content and does not guarantee it is safe, accurate, or free of scams.
6. Link-outs are not scanned by the hub's malware scanner (it can only scan files it stores). Watch R2 storage use, since R2 does not email when the free allowance runs out (see the free-tier monitoring note under Tech stack). Link-outs and hosted bundles are both **public/free** storage types for now.

**Following system**: users can follow/unfollow other users. Followed users' new posts/uploads appear in the follower's notifications.

**Notifications**: a real panel (not just an icon) — new replies, questions on your posts, activity from people you follow.

The correct sequence: (1) generate fresh embeddings for *all* existing content using the new model, storing them in a new column alongside the old ones, without touching live search yet; (2) once every piece of existing content has a complete new-model embedding, switch live search to read from the new column and start using the new model for anything created going forward; (3) only after confirming the new setup works correctly, delete the old embeddings. ## Translation

- **Three languages are written and human-reviewed — English, Simplified Chinese, Traditional Chinese — and any other language is added automatically by AI (decision confirmed by Clara).** The language list is open-ended: those three are the reviewed originals, everything else is "AI-translated". Chinese stays two separate options (Simplified and Traditional). **Spanish and French (2026-10-09 gap review):** the prototype also carries Spanish and French landing-page lines, but Claude drafted those and **no human has reviewed them**, so they are **not** in the reviewed set. Until a named person reviews them, treat them like any other auto-added language and label them AI-translated. Open item 20 asks who, if anyone, will review them.
- **First-visit language auto-detection, confirmed and added**: on first arriving at aoe.ai, the site reads the visitor's browser/device language setting and automatically shows English, Simplified, or Traditional Chinese to match, whichever of the three it is. If the visitor then manually picks a different language via the header switcher, that manual choice overwrites the auto-detected one (and, per the profile rule above, gets saved going forward).
- **Auto-expanding to any newly detected language — confirmed by Clara, overriding an earlier recommendation against it.** When a visitor's browser language isn't on the list, the hub translates the **whole interface** into that language with AI, stores it, and **permanently adds it to the language list** for everyone. Trade-off, recorded and not to be re-litigated: interface text for those languages is AI-generated and not human-reviewed before it goes live, so the "hand-reviewed interface text" principle below now applies to the three original languages only. **Recommended safeguards (cheap, keep the decision, reduce the risk):** (a) label AI languages as machine-translated wherever the language is detected or chosen; (b) create a new language only from a genuine browser session (not bots), only for real language codes, with a daily cap on new languages; (c) store each interface string per language in the database with a `source` of `reviewed` or `ai`, so the Creator can later correct a string or replace a whole language with a reviewed one; (d) generate once and cache forever (the same cache-once pattern as content); (e) Simplified↔Traditional stays on the deterministic converter. The prototype shows the first-visit banner, a new language appearing in the list after a short simulated "translating…" step, and the machine-translated notice. It **fakes** the AI translation and keeps landing-page text in English for languages it has no sample text for.
- **Translate-by-default, not opt-in-per-click.** Once a user sets their language (at sign-up, the header switcher, or Settings), **everything they see is shown in that language automatically** — post titles, summaries, comments, file introductions, and interface buttons — with no manual translate action needed, including in browsing/list views (File Board grid, Experience Board feed), not just full detail pages. This was deliberately changed from an earlier draft where translation was opt-in per item via a small "Translate" button — that model has a real problem: someone browsing a list of titles they can't read at all has no way to even tell what's worth clicking into, and manually translating every single item in a feed doesn't scale. The corrected model matches the established "See translation / See original" pattern used by platforms like Facebook and Twitter/X.
- **This applies everywhere text appears, not just File Board and Experience Board — explicitly including the moderation dashboard used by Creator/Watchers/Deacons.** This matters for real moderation reasons: a report or a flagged post could be in any language, and whoever's reviewing it needs to actually understand what they're reviewing regardless of what language it was originally written in — the same "Translated from [language]" toggle applies there too.
- **Per-item toggle back to the original**: each translated piece of content shows a small label, e.g. "Translated from Chinese" — clicking it reveals that item's original, untranslated text; clicking again reverts to the translated version. In the prototype the labels read "Translated from Chinese · Show original" and, once toggled, "Showing original (Chinese) · Show translation"; the labels are themselves interface text in the viewer's language. **If a piece of content is already in the viewer's own language, no label appears at all** (nothing to translate, nothing to toggle) — don't show a pointless "Translated from English" tag on English content for an English-reading viewer.
- Translation covers **both** the hub's own interface **and** user-generated content — post titles/descriptions, file introductions, and comments.
- **Cost note**: the cache-once pattern below applies the same way regardless of whether translation is triggered by a manual click or automatically on first view — each piece of content only ever gets translated once per language, cached, then served to everyone after that. Moving to translate-by-default means short titles/summaries in list views get cached translations too (not just full post bodies), which is a small amount of additional cheap, short-text translation work, not a meaningful cost shift.
- **Downloaded file contents themselves are never translated** — only the surrounding text (titles, descriptions) is. This should be stated clearly to users so expectations are set correctly.
- **Cost-saving pattern**: cache a translation the first time it's requested and serve the cached version to everyone after that, rather than re-translating on every view. Only genuinely new/uncached content should trigger a new translation call.
- The language picker should be available even to logged-out visitors (in the header), since people need to read the pitch in their own language *before* deciding to sign up — not just after.
- **A signed-in user's language choice is saved to their profile**, so it follows them automatically across devices — they shouldn't need to re-select their language every time they sign in somewhere new.
- **Translation model decision (Phase 6)**: use the *same* AI connection already handling RAG chat for translation too, rather than adding a dedicated service (Google Translate, DeepL). Reasoning: avoids a third API/account to manage; modern LLMs handle English↔Chinese translation well, especially with surrounding context; the cache-once pattern above already limits how much translation volume affects cost; and it stays consistent with the swappable-model architecture — whatever model handles chat also handles translation, through the same swap point. If a smaller self-hosted model is used later to cut cost, translation quality could dip slightly versus a dedicated service — not a dealbreaker, and a dedicated service could be added later as a contained addition if quality genuinely disappoints.
- **Translation must only translate stored posts, looked up server-side — never accept arbitrary submitted text.** Important security requirement found during implementation: if the translation endpoint accepted any text a caller sent, anyone on the internet could use the hub as a free translation service. Translation always operates on a specific, already-stored piece of content by its ID, looked up server-side — never on raw text passed in from outside.
- **Always use the hub's own shared API key for translation, never a member's personal key — this reverses the original assumption that bring-your-own-key would cover both chat and translation.** Found during implementation: since translation now happens automatically just from scrolling a feed (per translate-by-default above), using a member's personal key would silently spend their own money/quota without them deliberately asking for each one. Bring-your-own-key applies only to deliberate chat/RAG questions a user explicitly asks — never to passive, automatic translation. Once a piece of content has been translated, the result is cached, so every later reader gets the cached version with no new API call from anyone's key. *(An older paragraph that said a member's own key would also pay for translation was deleted on 2026-10-09 because it contradicted this one; Claude Code asked for it to be removed.)*
- **Simplified ↔ Traditional Chinese conversion uses a deterministic converter, not the AI model.** This is a well-defined, rule-based transformation (not something needing language "understanding"), so a standard free converter library is faster and more consistent than an AI call. The AI model is only used for actual English↔Chinese translation, which does need real understanding.
- **Fixed interface text (buttons, menus, labels) uses hand-written, human-reviewed English/Simplified/Traditional versions (Spanish and French are drafts, not reviewed; see above) — written once, not generated by AI per request.** This is different from user-generated content (posts, comments, file introductions), which genuinely needs AI translation since it can't be pre-written. Interface strings are a small, fixed, known set — a reviewed static file for each of the three languages is faster, cheaper, and more consistent than repeatedly asking an AI to translate the same "Sign up" or "Download" button. The AI translation pipeline is reserved specifically for dynamic, unpredictable member-created content. **Exception, by Clara's decision:** for languages beyond the three reviewed ones, the same small fixed string set is AI-translated once and cached (see auto-expansion above).

If it ever stops working out, the fallback is a small paid server (see "Fallback" below).
  - **Can it scan several files at once? Yes.** Cloud Run can send several requests to one instance at the same time (a "concurrency" setting; its default is high, so set it low for 4 GiB, e.g. 2–4), ClamAV's service (clamd) scans in several threads, and Cloud Run can start a second instance. With a limit of 2 instances and concurrency of 3, about six files can be scanned at the same moment; extra files wait in a queue in the hub and are scanned as capacity frees up. Memory is the limit, so test with real 50 MB zips before choosing the numbers.
  - **How a scan works.** A member's zip goes to a private quarantine bucket in R2. The hub's backend asks the scanner (Cloud Run, private, authenticated) to scan it, passing a short-lived download link instead of the file (Cloud Run reportedly limits HTTP/1.1 request bodies to about 32 MiB, less than a 50 MB zip; verify). The scanner downloads it, runs ClamAV (with zip contents unpacked and scanned) and answers clean, infected or error. Clean: the file moves to public storage. Infected: deleted, uploader told, event logged. Error or scanner down: the file stays hidden and the upload waits; the scan is never skipped. Files that cannot be fully scanned (encrypted or over-limit archives) are rejected.
  - **How to avoid being charged too much (do all of these).** (1) **Set maximum instances to 1–2** (default is 100; Google calls this a cost-safety limit). Worst case at 2 instances busy all month is roughly $170 and at 1 instance roughly $83 (a calculation from the listed rates of $0.000024 per vCPU-second and $0.0000025 per GiB-second, 4 GiB and 1 vCPU, not a Google figure). (2) **Keep minimum instances at 0**; idle machines are billed. (3) **Make the service private (require authentication)** so only the hub's backend can call it; requests denied by access rules are not billed, so strangers cannot run up the bill. Honest tradeoff: restoring from incrementals needs the full chain (the original base backup plus every increment since), slightly more involved than loading one file — worth it for the storage savings.

This is opt-in, not a default safety net. Set a low cap (e.g. $1–2) right away — given the tiny actual backup size, this gives an early warning long before any real charge could happen.
- **On self-hosting the database in the future**: explicitly discussed and deliberately deferred, not ruled out. Because Supabase runs standard PostgreSQL (not a proprietary format), a full export/migration to a self-hosted Postgres server is a clean, well-understood path any time later, using `pg_dump` (export) and `pg_restore` (import) — the same tool already used for routine backups. Reasons to stay on Supabase for now: no server to personally secure/patch/monitor, no need to hand-build the auth system (a genuinely higher-risk undertaking than using a well-tested existing one), and no added cost. If self-hosted later: gains full control and removes the `pgvector`-on-shared-hosting limitation entirely (a fully-controlled server has no such restriction), but adds real ongoing responsibility — crash recovery, attack monitoring, patching, and incident response become Clara's job rather than Supabase's, even though most of that can itself be automated (process managers like `pm2`/`systemd` for auto-restart on crash, `fail2ban` for repeated-login-attempt blocking, unattended security updates, free uptime monitoring like UptimeRobot). Don't build anything during the initial build that would make a future export harder than it needs to be.
